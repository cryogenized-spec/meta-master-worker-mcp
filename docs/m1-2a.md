# M1.2a — Authorisation Worker and credential-vault foundation

**Implementation stage:** split OAuth issuer Worker and AES-256-GCM cryptographic primitives. This is not a connected Meta account, a completed login flow, or a public deployment.

## Added

- Independent `apps/auth/` Cloudflare Worker using `OAuthAuthorizationServer` from the pinned Workers OAuth Provider 1.2.4.
- Service-binding `validateToken(resource, token)` method for the resource Worker.
- An explicit `AUTH_ENABLED=true` startup guard: valid issuer/resource URLs and an actual `OAUTH_KV` namespace are required to activate the OAuth provider.
- **Permanent /authorize denial during this increment.** No operator sign-in, consent page or call to `completeAuthorization()` exists, so the Worker cannot issue a new grant. The provider's metadata and token endpoints can be enabled only after configuration, but there is no UI that can authorise a user yet.
- Read-only scope advertisement (`mcp:read`), with no `mcp:write` granted.
- Worker bundle dry-runs for **both** Cloudflare Workers; no deployment.
- `src/storage/token-crypto.ts`: authenticated AES-256-GCM encryption, random 96-bit IVs, envelope versioning, additional authenticated data that binds operator/connection/platform, and non-leaking errors.
- `migrations/0001_meta_connections.sql`: D1 schema for ciphertext-only connection records and audit metadata. **No D1 is bound or provisioned.**
- Unit tests for configuration, no-consent boundary, cryptographic round-trip, wrong operator, wrong key and tampered ciphertext.

## Deliberate security boundaries

- We must **not** implement `/authorize` by accepting a claimed user ID or a request-provided `approved` Boolean. Future authorisation must verify a genuine operator login and unforgeable per-client consent before `completeAuthorization()`.
- No personal account names, IDs, Cloudflare namespace IDs, Meta tokens or encryption keys are committed.
- Never enable `AUTH_ENABLED` in production before verified operator identity, consent, callback, CSRF, PKCE, state and revocation tests.
- `META_TOKEN_ENCRYPTION_KEY` will be a 32-byte base64url-encoded Cloudflare **secret**. The code does not generate, persist or log a key.
- OAuth Provider's `OAUTH_KV` is distinct from application D1. D1 will hold only ciphertext of Meta provider credentials and connection metadata.
- No Meta Graph API request is connected to an MCP tool at this stage.

## Required before an operational M1

1. Choose operator identity source: GitHub OAuth, Cloudflare Access or another audited identity provider.
2. Implement user sign-in and the provider's `beginConsent()`, `approveConsent()` and `denyConsent()` helpers with browser-bound state.
3. Test against a local OAuth resource Worker for real token issue, resource-bound audience validation, scope denial, expiry, reuse and revocation.
4. Configure private Cloudflare OAuth KV and D1 bindings; apply and test the schema and ciphertext storage adapter.
5. Implement authorised Meta OAuth and Page permission introspection.
6. Deploy **only with explicit approval** and private secrets configured in Cloudflare.
