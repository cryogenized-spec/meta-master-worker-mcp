# M1.2c — D1 encrypted Meta credential adapter

**State:** source implementation and tests only. No Cloudflare D1 database, encryption key, Meta OAuth connection or production deployment has been provisioned.

## Capabilities

- Connection creation encrypts the Meta token with the existing AES-256-GCM helper before inserting into D1.
- Operator identity, connection ID and platform are authenticated additional data for encryption, preventing ciphertext from being copied between connections.
- Bound SQL parameters are used for every query; no token is interpolated into SQL source.
- Create and connection-audit insert share a Cloudflare D1 batch, which is transactional.
- Token reads are scoped to both the authenticated operator ID and connection ID; expired tokens are withheld.
- Account listing selects **only metadata** and excludes ciphertext columns from the SELECT statement.
- Local disconnect atomically records an audit event for an owned row and deletes the stored connection.
- Duplicate connection IDs fail on the primary key rather than overwriting an existing operator.
- Connection creation and lookup are **internal services**, not MCP tools. No public endpoint was introduced.

## Limitations and pending work

- Tests use a D1 fixture and validate query scoping/encryption contracts. They do **not** apply the schema to a real D1 database or prove transaction rollback.
- Disconnect is **local only**. Provider-side token revocation and consent revocation remain separate work.
- No token refresh, token key rotation, Meta token expiry introspection or Graph API client exists.
- The private META_DB binding and META_TOKEN_ENCRYPTION_KEY Cloudflare Worker secret must be configured separately after explicit approval.
- A production-grade future key-rotation migration must support old/new key identifiers, transactional replacement and audited failure/retry.
- For connection creation, the caller must derive operatorId from a verified server authentication context; never accept it as an arbitrary MCP tool input.
