# M1.2d — Local OAuth and D1 runtime integration

**Status: local integration verified in GitHub Actions. Live account integration is not complete.**

This milestone connects the existing OAuth and encrypted-token storage code to *real local Cloudflare Workers runtime bindings* in CI, rather than only mocking the database and OAuth provider.

## Verified against actual local workerd

[GitHub Actions CI run #43416793550](https://github.com/cryogenized-spec/meta-master-worker-mcp/actions/runs/43416793550) ran on Node 24 with `npm ci`, TypeScript, unit tests, integration tests and Wrangler dry-run bundles for both Workers.

### D1 and KV

- Applies the existing D1 schema SQL to a disposable, in-memory workerd D1 database.
- Creates, reads and decrypts stored Meta-token *fixtures*; the SQL row contains AES-GCM ciphertext, never the plaintext fixture.
- Restricts reads and metadata listing to the requested operator; tests prevent cross-operator disclosure.
- Verifies expiry handling, owner-scoped disconnect and audit records.
- Verifies a duplicate connection is rejected and a failed SQL batch rolls back.
- Exercises actual Worker KV operations, including TTL, get and delete.
- No production D1 or KV namespace is created, accessed, or modified.

### OAuth Provider

- Uses the pinned `@cloudflare/workers-oauth-provider` with actual local Worker KV binding.
- Creates an isolated test OAuth client and runs authorization parsing, informed-consent transaction, browser binding and one-time handle enforcement.
- Tests upstream state recovery and replay rejection *without contacting GitHub*.
- Simulates the result of successful identity verification with an explicitly test-only operator ID.
- Exchanges an authorization code for a resource-bound token using the real token endpoint.
- Confirms correct audience acceptance, unknown-resource rejection, one-time authorization-code exchange, and token invalidation after client deletion.
- **Found and fixed an existing production defect:** OAuth user IDs cannot contain a colon. The GitHub operator ID format has been corrected from `github:<id>` to `github-<id>`.

## How to run locally

```sh
npm ci
npm run check
npm run build
```

The `check` script runs the isolated standard unit tests *and* the Cloudflare Vitest integration tests using the official `@cloudflare/vitest-plugin`. No remote secrets or Cloudflare account are necessary.

## Boundaries not yet passed

**This is not a production deployment or live OAuth sign-in.** The tests use a fixture client and operator identity, not the actual GitHub OAuth callback, consent in a real browser, or real ChatGPT/Claude MCP clients. They also do not send requests to Meta.

Still required before M1 can be called complete:

1. Register a real GitHub OAuth application with exact callback `<ISSUER>/oauth/github/callback`, configure the numeric allowlisted operator ID and store the client secret privately.
2. Provision the Cloudflare OAuth KV namespace and the separate issuer and resource Workers with their exact URLs and private service binding.
3. Provision a real D1 database, apply the schema with Wrangler and test migrations/backups/recovery with a throwaway database first.
4. Configure a random 32-byte `META_TOKEN_ENCRYPTION_KEY` as a Worker secret, with no values in the public repo; design key rotation before placing real tokens.
5. Exercise the **complete** browser GitHub OAuth login and consent flow, actual token issue/validation/revocation and wrong-scope, wrong-audience, stale-token, denied-consent and cross-operator scenarios across both Workers.
6. Only then implement Meta OAuth, permission diagnostics, refresh/revocation and first authorised Page discovery.

**Production safety:** no GitHub Actions job deploys these Workers. `AUTH_ENABLED` must remain off until explicit operator approval and live test gates are satisfied.

## Technical notes

- The official Cloudflare Vitest plugin is used instead of standalone Miniflare, which had an older binary that did not support our Worker compatibility date.
- Standard unit suites remain Node-hosted and separate from workerd-backed integration suites.
- SQL migration statements are submitted individually inside the test harness; remote migrations are **not** performed by CI.
- Any real OAuth tokens, app secrets, customer data or production database identifiers must never be included in test fixtures, issues, logs or commits.
